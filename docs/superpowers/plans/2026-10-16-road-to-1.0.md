**Goal:** Ship a 1.0 whose code is organized like portolan-registry-qgis (QGIS-free `core/`, `qgis_io/`, `gui/`, thin `plugin.py`), whose GeoParquet/DuckDB machinery is the vendored geoparquet-io embeddable core rather than a third parallel implementation, protected by a regression test suite built *before* the refactor, with the open issue backlog resolved or explicitly deferred.

**Architecture:** Four-layer package enforced by import-linter: `vendor/gpio/` is geoparquet-io's embeddable core synced as source (QGIS plugins cannot depend on PyPI) — covering resolution, bbox predicates, hardened connection setup, format writers, S3/remote config; plugin-own `core/` holds presets, download planning, and the partition pruning (file-name decoders and the Overture STAC lookup — these stay here permanently; gpio#1309 was closed 2026-10-17, PR gpio#1314 closed: gpio's boundary is "explicit file list in") with zero `qgis`/`PyQt`/`osgeo` imports; `qgis_io/` holds workers, layer loading, QGIS-side CRS conversion, and the DuckDB installer; `gui/` holds the dialog and map tools. Tests mirror the split: `tests/core/` runs headless on plain Python (fast CI job and — finally — locally on macOS, where the QGIS module can't be imported), `tests/in_qgis/` keeps the QGIS-Docker matrix (3.34/Qt5 and 4.2/Qt6).

**Tech stack:** Python ≥3.9 (QGIS LTR floor — the vendored core honors it too), DuckDB (imported inside functions only; no version pin inherited from gpio), PyQt5+PyQt6 via fully-scoped Qt enums, pytest + pytest-qt, ruff, import-linter, mkdocs for the doc site.

**Spec:** Chris's request of 2026-10-16 plus `~/Downloads/a-shared-geoparquet-core.md` (the Oct 15 three-repo survey). Tests before refactor; portolan-registry-qgis shape; shared machinery lives once, in gpio; stac-geoparquet (#56) out of scope — closed.

## Global constraints

- Plugin-own `core/` and `vendor/gpio/` must never import `qgis`, `PyQt5`, `PyQt6`, `qgis.PyQt`, or `osgeo`; import-linter enforces this in CI.
- Every `import duckdb` stays inside a function body, never at module top level — the plugin must import cleanly when DuckDB is absent so it can tell the user to install it.
- `vendor/gpio/` is synced by script with the source commit recorded; never hand-edited. A behavioral divergence found during the swap becomes an upstream gpio PR or a documented intentional difference, never a silent local patch.
- Qt enums fully scoped (`Qt.ItemDataRole.UserRole`) so Qt5 and Qt6 both work.
- Public behavior frozen during Phases 1–2: same presets, same SQL effects, same output files, same QSettings keys. Intentional changes are their own PRs with CHANGELOG entries.
- `gpq_downloader/utils.py` keeps working as a re-export shim until 1.0; deleted in the 1.0 release PR.
- Active work is in flight on this repo — phase work happens in git worktrees, one branch per task.
- Releases keep going out during the roadmap (0.9.x → 0.10 → 0.11 → 1.0); the refactor never blocks a bug-fix release.

## Review focus

Failure modes the refactor could introduce that no existing test pins — each gets a characterization test in Task 1.1/1.2 before any code moves (these also arbitrate the gpio swap: where gpio's behavior differs from ours, the test flags it for an explicit decision):

1. A preset URL that resolves through *both* rewriting paths (source.coop proxy glob + dotted-bucket path-style conversion) must emit the same final S3 URL after resolution moves to the vendored core.
2. Overture downloads must still prune to the partition files the AOI touches; a silent pruning regression returns correct-looking but incomplete data.
3. CRS handling for non-4326 sources: the metadata parsing moving to QGIS-free code must keep producing the same reprojection decisions — today's "pure" logic secretly leans on QGIS types, and the seam (core returns authid strings/tuples, `qgis_io/crs.py` converts) must be designed, not discovered.
4. Cancellation mid-download (`CancellableConnection`, `Worker.kill`) must still interrupt DuckDB and leave no partial output file loaded as a layer — especially across the QThread→QgsTask move in #197.
5. QSettings persistence (checkbox states, last extent, radio buttons) must survive the dialog split — keys are string literals scattered through `dialog.py` and must be centralized first, or saved states silently reset for every user.
